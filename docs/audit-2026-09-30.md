## D1 — `sticker-drag` no se compila: el behavior no hidrata en producción

**Severidad: ALTA. Defecto real, de cara al usuario.**

`packages/builder42/tests/sticker.test.ts` falla:

```
FAIL tests/sticker.test.ts > F23b — todo behavior con runtime tiene su bundle declarado
     > sticker-drag → BEHAVIOR_ENTRIES.stickerDrag
AssertionError: build-runtime.mjs no compila "stickerDrag": el behavior "sticker-drag"
no hidrataría en el sitio exportado
  expected '#!/usr/bin/env node…' to match /\bstickerDrag:\s*"behaviors\//
```

El test tiene razón. Cadena verificada:

- El behavior está **registrado**: `builder/registry/behaviorRegistry.ts:50` importa
  `stickerDragBehavior` (`type: "sticker-drag"`).
- Está **en uso** por un layout que se envía: `builder/registry/layouts/pages/pizzeriaPage.ts:1191`
  → `behaviors: [{ type: "sticker-drag", options: { axis: "both", bounded: true } }]`.
- El runtime **existe**: `src/runtime/behaviors/stickerDrag.ts`, que se auto-registra en
  `window.__pbBehaviors.enhanceStickerDrag` (líneas 183-184).
- Pero `scripts/build-runtime.mjs` **no lo declara**: en `BEHAVIOR_ENTRIES` solo aparece
  `sticky: "behaviors/sticky.ts"`; no hay ninguna entrada `stickerDrag`. Son 17 behaviors + 4
  actions + 2 standalone = **23 entradas**.

Por qué no se nota en esta máquina: `src/runtime/dist/` tiene **24** bundles — las 23 declaradas
**más `stickerDrag.js`**. Ese archivo sobrevive de un build anterior porque `build-runtime.mjs`
compila con `emptyOutDir: false`. Y no está versionado:

```
git check-ignore -v → .gitignore:6:dist/   packages/builder42/src/runtime/dist/stickerDrag.js
git ls-files        → error: pathspec … did not match any file(s) known to git
```

Consecuencia: en un clone limpio / CI / deploy, `postinstall` corre
`pnpm --filter builder42 build:runtime` y `stickerDrag.js` **no se genera**. El glob de
`export/runtimeBundles.*` no lo encuentra, así que `sticker-drag` no se inyecta ni en el Preview
del canvas ni en el sitio publicado: el sticker del hero de `pizzeriaPage` se ve por CSS pero
**no se puede arrastrar**. Es el mismo modo de fallo que ya documenta la cabecera de
`build-runtime.mjs` para el Modal (commit `9cbefe0`).

Arreglo: añadir `stickerDrag: "behaviors/stickerDrag.ts"` a `BEHAVIOR_ENTRIES`.

## D2 — ninguna suite raíz ejecuta `packages/builder42` ni `packages/product-tour`

**Severidad: MEDIA-ALTA. Es la razón por la que D1 pasó desapercibido.**

`vitest.config.ts` (raíz) limita el include a:

```ts
include: ['tests/unit/**/*.test.ts', 'tests/integration/**/*.test.ts'],
```

Y los scripts raíz nunca invocan los paquetes:

```
test     => vitest run
test:all => pnpm test && pnpm test:e2e && pnpm test:coverage
```

Ambos paquetes tienen su propio `vitest.config.ts` y script `test`, pero hay que llamarlos a mano:

- `packages/builder42` — **26 archivos, 310 tests** (justo la feature que se está verificando).
- `packages/product-tour` — **15 archivos, 106 tests**.

Es decir, **416 tests** de la feature nueva quedan fuera de `pnpm test` y de `pnpm test:all`. Nota
que `typecheck` sí cubre los paquetes (`tsc -p packages/builder42 --noEmit`), así que el hueco es
solo de tests. Arreglo: añadir los paquetes al `test:all` raíz (o usar vitest workspaces/projects).

## D3 — invariante obsoleto: `standaloneChrome` ahora gatea DOS anclas

**Severidad: baja (tests desactualizados, sin impacto en el embed de Maildrill).**

Tres fallos, una sola causa:

```
FAIL tests/tourSteps.standaloneChrome.test.ts (×2)
  AssertionError: expected [ 'pbx.header.identity', …(20) ] to include 'pbx.settings.prefs'
FAIL tests/tourSteps.flags.test.ts:223
  AssertionError: expected [ 'pbx.canvas.dragNode', …(21) ] to deeply equal [ … ]
```

`tourSteps.ts:705` empuja el paso `settingsPrefs` **solo si `!config.standaloneChrome`**, con
justificación explícita en el comentario (en standalone esa sección monta `SiteFileActions`, no
`EditorPreferences`, y las preferencias las cubre el paso `profileMenu`). Es decisión deliberada.

Pero los tests codifican el invariante anterior:

- `tourSteps.standaloneChrome.test.ts` construye `OTHER_ANCHORS` como "todas las anclas menos
  `pagesBreadcrumb` y `profileMenu`" y exige que **todas** estén presentes con cualquier
  combinación de flags. El título del describe lo dice: *"standaloneChrome gatea SOLO
  pbx.profileMenu"* — eso ya no es cierto. Falla en las dos filas con `standaloneChrome: true`.
- `tourSteps.flags.test.ts` exige *"exactamente las 18 anclas del registro"*; el registro ya tiene
  más (el diff muestra 21-22) y `ADVANCED_CONFIG` excluye `settingsPrefs`.

Sin impacto para Maildrill: la ruta `/dashboard/landings/editor` es **embebida**
(`standaloneChrome: false`), así que ahí `settingsPrefs` sí se emite. Arreglo: restar
`settingsPrefs` de `OTHER_ANCHORS` y actualizar el conteo esperado.

## D4 — los 5 fallos e2e del landing editor son tests obsoletos frente a la cadena F29

**Severidad: baja como producto, media como cobertura (esos 5 tests hoy no prueben nada).**

Resultado del describe `landing editor tour`: **8 pasan, 5 fallan** (15, 16, 23, 24, 25, 26 en la
numeración del run; 15/16 comparten causa con 26).

La cadena F29 partió el tour plano único en **cuatro** tours (`tourSteps.ts:818`,
`BUILDER42_TOUR_IDS`) con un mapeo explícito de anclas por tour (D-F29.20):

| tour                 | anclas                                                                                                             |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `builder42.overview` | headerIdentity, sidebarTabs, canvasFrame, inspectorTabs — **4** (upstream tiene 5; `headerDownload` no se portó)    |
| `builder42.library`  | sidebarPalette, sidebarDragHint, sidebarTemplates — 3                                                              |
| `builder42.canvas`   | canvasFrame, settingsLayers, canvasNodeActions, canvasInlineText, canvasDragNode, **toolbarViewport, toolbarViews**, toolbarHistory — 8 |
| `builder42.rightPanel` | inspectorTabs, inspectorBreakpoints, settingsTabs, settingsPages, settingsLanguages, settingsTheme, pagesBreadcrumb — 7 |

`tour.spec.ts` sigue escrito contra el tour plano anterior. Medido en vivo (el tour que auto-arranca
es `overview`, 4 pasos):

```
INICIO   popovers:1 overlays:1 active:[pbx.header.identity]   "Name and autosave"            1 of 4
ARROW 1  popovers:1 overlays:1 active:[pbx.sidebar.tabs]      "Components and templates"     2 of 4
ARROW 2  popovers:1 overlays:1 active:[pbx.canvas.frame]      "The canvas"                   3 of 4
ARROW 3  popovers:1 overlays:1 active:[pbx.inspector.tabs]    "Content, style, interactivity" 4 of 4
ARROW 4  (no-op en el último paso, D21)                                                      4 of 4
```

`viewsAnchor:1` y `viewportAnchor:1` en todo momento: **los anchors existen en el DOM**, simplemente
ya no pertenecen a este tour. Causas por test:

- **15 y 16 — `markLandingTourSeen()` no tiene efecto.** El helper escribe las claves planas
  `pb:tourSeen` / `pb:tourVersion`, que `useLocalConfig.ts:97-100` declara **legacy desde D-F29.18**
  ("ya no las lee ni las escribe nadie"). La fuente de verdad es el record `pb:tours`. Comprobado:

  ```
  A) localStorage pb:tourSeen=true   → popovers:1   (el tour arranca igual)
  B) localStorage pb:tours={"builder42.overview":{seen:true,completed:true,version:1,…}}
                                     → popovers:0   (suprimido correctamente)
  ```

  Es decir **el producto suprime bien**; el helper apunta a la clave equivocada. Forma real que
  escribe el editor: `{"builder42.overview":{"seen":true,"completed":false,"version":1,"lastStepIndex":0}}`.

- **16 y 26 — el botón "View the guided tour" ya no relanza el tour.** Desde D-F29.27 abre el
  selector `TourChooserModal`. Comprobado tras el click:

  ```
  popovers:0  dialogs:1  "Pick a tour — Each one walks through a different part of the editor…
               Overview… Library and page templates…"
  ```

  Los tests esperan `.driver-popover.md-tour` con count 1 inmediatamente; ahora hay que elegir tour
  primero (o llamar `startBuilder42Tour(tourId)`).

- **23 — `pbx.toolbar.views` / `pbx.toolbar.viewport` se movieron al tour `canvas`**, y además en
  orden **invertido** (viewport antes que views). El test los espera como pasos 2 y 3 del tour que
  auto-arranca.
- **24 — `sidebarTemplates` se movió al tour `library`**, no está en overview.
- **25 — `settingsLayers` está en `canvas`; `settingsPages` / `settingsLanguages` en `rightPanel`.**

Arreglo: reescribir estos 5 contra el tour correcto (arrancándolo por id) y actualizar el helper a
`pb:tours`.

## Fuera de alcance (no builder42)

Registrado solo para que no se confunda con lo anterior:

- **`auth.setup.ts` / Playwright completo.** `AUTH_SECRET` en `.env` es solo el comentario de ayuda,
  `/api/auth/csrf` → 500 (`MissingSecret`), el setup cae y arrastra 90 tests. Ya está en la bitácora
  (B6/B28) y se sortea con `--no-deps` + `SKIP_AUTH_FOR_BUILDER_WORK`. Detalle nuevo medido: el
  bundle SSR hornea `secret: ""`, y como `""` no es nullish el `?? process.env.AUTH_SECRET` de
  `auth.config.ts:26` nunca entra — inyectar la variable en el daemon **no** rescata un build hecho
  con `.env` vacío (probado en un puerto aislado: seguía dando `MissingSecret`). `||` en vez de `??`
  lo haría robusto. El `.env` no se tocó: son credenciales del entorno.
- **Editor de email, 3 tests:** fallaban por arranque en frío de `astro dev`
  (`waitForLoadState('networkidle')` a 30 s). Reejecutados en caliente: **pasan** en 6.2 s / 7.2 s.
- **Editor de email, 1 test** (`Escape yields to the send-test dialog`, D11): el tour se cierra en
  el paso 14 antes de alcanzar el ancla buscada. Es EmailBuilder.js, no builder42 — sin diagnosticar.
- **Gates del repo:** `pnpm lint` falla con 3 errores (`react-hooks/exhaustive-deps` no registrada
  en `eslint.config.js` + `past`/`future` sin leer en `AutomationBuilder.tsx`) y `pnpm typecheck`
  cae en Windows porque `scripts/typecheck.mjs` lanza `node_modules/.bin/tsc` sin `shell: true`
  (0 errores de tipos reales en app). Backend: 3 fallos en `email-validation.test.ts` por
  `dns.resolveMx` → ECONNREFUSED en este host (tests no herméticos, dependen de DNS en vivo).

## Resolución

Todo lo de los dos editores quedó corregido en esta misma sesión.

| #   | Qué era                                        | Arreglo                                                                                                           |
| --- | ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| D1  | `sticker-drag` sin compilar                    | `stickerDrag: "behaviors/stickerDrag.ts"` en `BEHAVIOR_ENTRIES` de `build-runtime.mjs`                             |
| D2  | 416 tests de paquetes huérfanos                 | script raíz `test:packages`, cableado en `test:all`; README actualizado                                            |
| D3  | invariante `standaloneChrome` obsoleto          | `OTHER_ANCHORS` excluye `settingsPrefs` + aserción del gating inverso; el test de "18 anclas" pasó a ser la UNIÓN de los dos modos de chrome (sin número cableado) |
| D4  | 5 e2e contra el tour plano pre-F29              | helper a `pb:tours`, `startLandingTour()` vía `TourChooserModal`, `advanceUntilAnchor()`, cada test contra su tour |
| D5  | flake D50b                                      | fixture en dos fases, arrancada por `startMoving()` justo antes del sondeo                                         |
| —   | email D11 (`eb.header.actions`)                 | recorrido con `ArrowRight` en vez de clicks en "Next"                                                             |
| —   | flake `stepActivation` (aparecido al verificar) | `waitForTitle()` que sondea, en lugar del sleep fijo de 120 ms                                                     |

Detalles que conviene no re-descubrir:

- **D1 no era visible en local** porque `src/runtime/dist/` está gitignored y `stickerDrag.js`
  sobrevivía de un build viejo (`emptyOutDir: false`). Tras el arreglo lo genera el script
  (timestamp actualizado, mismo contenido: 2287 bytes).
- **D4, la trampa de verdad:** `shouldAutoStartTour()` suprime con `!(seen && completed)`, no con
  `seen`. Un tour visto pero NO completado **debe** volver a auto-arrancar (reanuda desde
  `lastStepIndex`), así que "ya visto" en un test es `completed: true`. Y hay que marcar los
  CUATRO tours, porque `zoneTourTriggers` se arma justo cuando el overview está completado.
- **D4, T12:** el bucle de medición sale en el paso "Listo" sin pulsarlo, así que el tour sigue
  abierto y su overlay se come el click que abre el selector del siguiente recorrido. Hay que
  pulsar Escape al cerrar cada tour (eso era un timeout de 180 s).
- **Email D11:** `eb.header.actions` es el paso **15 de 15**, con el botón ya en "Done". Varios
  clicks en "Next" no avanzaban (pasos 7, 10 y cuatro veces el 12) y uno acabó enrutando a
  `onDoneClick`, cerrando el tour — el B35/B36 que el propio spec documenta. `ArrowRight` también
  repite alguna pulsación, pero nunca destruye el tour.
- **Los dos flakes de `product-tour`** eran la misma clase de error: una espera de reloj de pared
  calibrada contra la duración del setup. Con la suite en paralelo no se cumple.
